# Native pointer: the Room as the record, the engine as the doorbell

*fleet-delivery mod 0.4.3, 2026-10-30.*

## The problem it removes

Seat-to-seat mail in the fleet was a Room file (the record) delivered by typing it into the recipient's prompt box (the transport). Every stall seen on the live seats in October 2026 was a stall of that transport or of the claim state that guards it, never of the record:

| ledger state | what it meant |
|---|---|
| `deferred:composer-busy` | the recipient's prompt box held a draft |
| `deferred:supervisor-hold` | the supervisor froze the inbox for a refresh handshake |
| `deferred:refresh-hold` | the runner's cycle file was not idle |
| `submitting:unresolved` | a claim with no submit in flight; everything behind it waited for an operator's `/delivery-reconcile` |
| (DaVinci, 2026-10-29 16:36Z) | a message typed during the clear landed as the first prompt of the new session, ahead of the resume |

## The design, after six review rounds

The first six rounds of review were spent on a design where the mod carried the body natively, matched it against the Room file, timed a confirmation window and read the transcript to decide "delivered". Each round opened a new seam in the same three places (the match, the clock, the confirmation). The shape that ships has none of them:

1. **Record unchanged.** `room_send` writes the envelope file into `<roomRoot>/inbox/<seat>/`; the per-seat ledger and the inbox/claimed/processed folders keep their meaning; read receipts, replay and audit stay file-based.
2. **A pointer, not the body.** The sender's mod hooks `tool.call` for `mcp__agent-room__room_send`; after the Room server answers, and before the tool's answer goes back to the model (the send is awaited inside the hook, bounded at 5 s, so no `$` is used after the hook returned), it sends `Room mail for <seat> from <sender>: <file>` plus one line telling the model to call `room_drain`. The receiver applies the decision table in item 4 to every peer delivery (`peer`, `peer-send-message`, and a task notification with that subkind). The pointer is addressed to the session id the recipient's marker carries (`$.session.send({ to: { sessionId } })`), never to a bare name: the engine resolves a name the way SendMessage does, and a subagent of the sender named like the seat would take it with `isDelivered` true. A `/clear` gives the recipient a new id and its next marker write carries it; a pointer to the old id is refused and the file waits for the tick. The engine queues it inside the recipient: a turn of its own when idle, otherwise read inside the running turn or in a new turn if it arrived in that turn's tail. Nothing to match, nothing to forge: a forged pointer drains real mail, harmlessly.
3. **The Room's own consumer reads.** The recipient's model calls `room_drain`, which returns the unread inbox and moves each file to processed/ as read. **Semantics change, documented:** the 0.3.0 tick delivered every Room file as its own prompt; `room_drain` collapses same-sender, same-thread messages, so two pointers from one sender on one thread yield one drain and the older message is consumed unshown (the vault's known supersede failure, now reachable on mod-owned seats). The pointer text therefore says: drain, and if the named file is not among the returned items, read it with `room_history` with `unread_only` false; a collapsed message is in processed/ and recoverable only that way. **Attention double-delivery:** a pointer read inside a running turn that the model does not act on would otherwise be followed by the tick claiming the file and submitting its body as a second turn, with the later drain returning nothing. The tick never claims while the main loop has a turn in flight (`turn.start` to `turn.complete`, including an aborted completion): its own submit could not enter before the session is idle anyway, and the file stays visible to the model's own `room_drain`; `turn.complete` ticks again and delivers mail that was not drained once its admission releases under row G of the table below. The mod writes nothing for a natively read file; to its tick a drained file is absent, a case it already handles. A file lies in exactly one of inbox/ (`room_drain`'s) and claimed/ (the tick's); the tail-turn timing limit is documented below.
4. **Two fences.** A seat is announced to only while its own mod publishes a fresh marker in the shared Room (`state/native/<seat>.json`: mod-owned, version 0.4.0 or later compared numerically, under 15 min old, rewritten at most every 5 min by the tick and by the tick's timer when a submit blocks the tick). The marker is published only while both holds (refresh cycle, supervisor) are clear and is retired by overwrite (`owner: retired`) under a hold, when the mod no longer owns the seat, and at session end (only a marker that reads back as this session's: this module's stamp, or this session's id after a plugin hot reload; a second session resolving to the same seat, such as a `claude -p` courier, never takes the live seat's marker down and never overwrites a fresh mod-owned marker that is not its own, so pointers cannot flap to the courier; when the file stops reading as the live seat's own and is not another live session's fresh marker, the live seat re-publishes on its next tick regardless of the 5-min throttle; a marker left by a dead process ages out in 15 min), so a held, supervisor-owned, older or parked seat gets no pointer and its tick or supervisor delivers the file; the sender falls back on its own. The marker is written with `$.fs.write`, not the atomic host write: a torn read on the sender's side parses as no marker and falls back, which is the safe side. The recipient fence follows this decision table. Neither fence runs while the mod is inert (`installRoot` unset). Turn bookkeeping resets through one resetTurnState(edge) helper at session start and end; all clears finish before waiters wake with sessionEnd true only at session end (false at session start). See row J below for the submit wait algorithm. The queue-level main-turn guard and per-item checks before and after composer reads protect Room files and job items; supervisor lifecycle legs remain exempt. The per-tick load cache shares pending reads and retains loaded bodies; null and error results are evicted.

   ```text
   FENCE TABLE (prompt.submit on a peer-origin text):
   A. Resolve installRoot/memoryRoot once per prompt. If memory is unresolved, drop BARE pointers with the memory root unresolved hold and enter MIXED mail unchanged, without reading file states, either hold file, or the clock. Sample files first outside the gate for THIS seat as described in E; read both holds only for BARE or UNREAD, afterwards in one Promise.all outside the gate. For each file, issue exists(claimedFile) and exists(inboxFile) together in Promise.all. No line for this seat: apply the other-seat rule below.
   B. Shape: BARE = every payload line is a pointer line, a pointer tail, or a KNOWN engine framing matched by ENVELOPE_LINE, with or without its optional colon; a prompt with no non-pointer lines is also BARE. Only known engine tag wrappers (cross-session-message and task-notification) are excluded; arbitrary angle-bracket lines are peer words and make the prompt MIXED. Every other payload line makes the prompt MIXED. In particular a generic-shape lead-in satisfying the colon rule is MIXED, even when it is the only non-pointer line: Here is what I got from the session: followed by a GONE pointer enters unchanged. Known framing such as Another Claude session sent a message: followed by a GONE pointer drops. FYI: and ordinary prose are MIXED too.
   C. BARE pointer: under a hold -> drop. When installRoot is set but roomRoot is unset, file states cannot be resolved: after the hold check, enter the pointer-shaped prompt unchanged (HEAD behavior), never classify it as GONE or drop it for having nothing unread. Addressed to another seat -> drop. Seat unresolvable -> drop. No hold: admit non-lifecycle UNREAD files only; CLAIMED and GONE files are not admitted. If nothing is admitted -> drop and log the states. Dropping because the files are GONE is allowed only for BARE prompts under B; a generic colon lead-in does not qualify. If admitting would exceed the 64 pending promptAdmissions entries, return { drop } with the cap reason, never forward unbound; the file waits for the tick. This cap drop applies only to BARE prompts; MIXED mail enters unchanged with nothing admitted. Log the cap once per process.
   D. MIXED mail: never rewrite text, including the catch path. Sample files first outside the gate. Read the two hold files afterwards, outside the gate, only for BARE prompts or when at least one file is UNREAD; MIXED mail quoting only GONE, CLAIMED, or UNKNOWN files performs no hold reads. File-state sampling uses the module's null-swallowing exists wrapper; a failed sample reads as UNKNOWN unless tickOwned, claimsInFlight, or a successful claimed/ sample establishes CLAIMED. A BARE pointer with any UNKNOWN state drops (fail closed). In MIXED mail an UNKNOWN sample for one file never strips admission from the others: admit = the non-lifecycle files whose state is UNREAD; UNKNOWN files are simply not admitted. Under a hold, MIXED mail naming an UNREAD file enters unchanged with nothing admitted and no file binding: the peer's words have no Room record, and the tick delivers the file after the hold. BARE still drops under a hold. A generic colon lead-in plus UNREAD enters unchanged, unbound under a hold and with that file admitted when no hold applies. At the promptAdmissions cap, enter MIXED mail unchanged with nothing admitted and leave the file to the tick, logging once per process. Both pointerHold's own check-error catch and the engine's not-called catch drop BARE and enter MIXED unbound through next(e). If the engine's catch settles the hook while a sample is pending, the settled flag prevents the abandoned body from binding admissions or calling next(e) again. After hold reads, a vanished provisional binding (for example, a session edge reset) is a fence failure: BARE drops and MIXED enters unbound. When memory is unresolved, enter MIXED unchanged and drop BARE.
   E. One module-level serialization gate orders only synchronous claim marking and file-state decision/binding. moveRoom checks admissionTurns for ordinary mail and, if unbound or a supervisor lifecycle leg, marks tickOwned.add(file) and claimsInFlight.add(file) synchronously in one gated microtask, then releases the gate before destination checks, child spawn, or any move/log disk I/O. A five-second spawn cannot delay a concurrent pointer fence beyond its file samples. The fence samples exists() for the files outside the gate, then enters one synchronous gated step to re-read tickOwned/claimsInFlight, classify, and bind: CLAIMED if tickOwned or claimsInFlight contains the file, or claimed/ exists; otherwise failed samples are UNKNOWN, inbox-only is UNREAD, and absent is GONE. No await separates classification from admissionTurns.set. A claim marked before the decision reads CLAIMED regardless of the earlier disk sample; an ordinary claim marking after binding checks admissionTurns under the gate and returns admitted without spawning. The tick silently skips admitted without a ledger deferral or a claimTries/deferrals increment. The file stays in inbox/ for the admitted pointer. Holds are read after sampling, outside the gate, only for BARE or at least one UNREAD file; provisional bindings protect files during those reads, survive intervening turn completions, and are released if the hold or abandonment drops the prompt. Their release turn/sequence is assigned immediately before forwarding, after holds finish. pointerHold binds directly and returns { drop } | { admission } | null, including cap handling. The fence never binds supervisor lifecycle files, whether named in BARE pointers or MIXED mail. Neither gated step awaits disk or a spawn; lifecycle classification also runs outside the gate. One promise-chain mutex helper creates independent serialMarker and serialized queues; jobs are invoked without arguments, preserve results/rejections, and leave a settled tail. On claim settlement, remove claimsInFlight and retain tickOwned only if the move landed, with no extra I/O in finally. An externally restored file remains CLAIMED while owned; an absent re-claim or session edge clears tickOwned. A session edge leaves claimsInFlight protecting pending claims until they settle. Turn-only checks still protect ordinary mail and jobs when a main turn starts during queue or composer reads.
   F. Removed (no stripping).
   G. admissionTurns holds a Set of bindings per file, one { seq, turnId?, token } for each prompt, never overwritten; the file releases only when every binding has released. Set turnId at admit time only when e.turnId names a running main turn (in mainTurns); otherwise leave it undefined. turn.complete(turnId, upTo) releases bindings with that turnId, and unbound bindings with seq < upTo; a bound admission releases at its turn's completion or at a session edge. upTo is turnSeq when the start was seen, otherwise turnSeq + 1. A bound prompt cannot overwrite an earlier unbound prompt: if P1 arrives unbound during t1 and P2 binds the same file to t1, t1 completion releases only P2; the next main turn's completion releases P1 and the file. No text matching or rebinding.
   H. A file is admitted iff admissionTurns has a binding for it; guarded(file) = turnInFlight() || admissionTurns.has(file). Each binding carries its prompt token (one counter string per peer-origin prompt.submit invocation). A downstream result or catch replay with drop !== undefined filters only bindings with its token; a rejected replay releases its bindings in finally; an empty Set removes the file. turn.complete and session.start/end remove a promptAdmissions entry when the last binding carrying its token releases. promptAdmissions tracks exact token/file lists until settlement (post-next deletion or catch replay) or the last binding releases. The hard cap is 64 entries: return { drop } for a BARE prompt beyond it; MIXED mail enters unchanged. Neither binds or tracks an admission; the file waits for the tick, and logErr is emitted once per process through the existing log path. Event identity is tracked outside frozen inputs; pending pointer checks are keyed by minted token. Copied catch events resolve the token from the matching-text FIFO of pending checks or failed prompts. A not-called catch releases its token through takePromptAdmission; a post-bind settled check also releases its bindings and removes its cap entry before dropping. Concurrent identical texts retain separate tokens; another prompt's admissions survive, and replay never rewrites text.
   I. Removed (no stamp).
   J. After both hold re-reads, start $.prompt.submit. Lazily arm one $.clock.after(TURN_WAIT_MS) deadline (60 minutes) on first entry into the turn WAIT branch; idle submits arm only their submit window. Reuse that deadline for subsequent WAITs. With a main turn in flight and no queued completion wake, race submit against turnEnded, session end, and that deadline; this WAIT consumes no window budget and arms no additional timer. When idle initially, or on each completion wake, grant a FULL config.submitTimeoutMs window. Keep wakes received during windows; same-millisecond completions each grant a window. Whenever a window consumes a queued completion, replace ended with a fresh promise even if more completions remain queued. A clockless fallback must wait for the NEXT completion, never reuse a settled ended promise. TURN_WAIT_ROUNDS = 6 caps all granted windows, including the initial window: total wait <= TURN_WAIT_MS + 6 x submitTimeoutMs. Never shorten a window with the WAIT deadline. After a window expires with no main turn and no queued wake, or after the sixth window, record submitting:unresolved. No $.clock.now() reads. session.start clears turn state and wakes parked waiters without ending the session wait loop; they re-evaluate and continue with submit windows. After session.end, return timeout immediately from either a turn WAIT or a submit window, with no final window, matching the clockless path. Record submitting:unresolved and release isTicking in the same tick; a submit discarded by the engine must not hold the tick for another ten minutes. If the initial submit-window arm throws while idle, do not park: return timeout at once, record submitting:unresolved, and release isTicking; the late submit.then(settle) corrects the outcome when the engine settles. When a main turn IS in flight, retain the clockless race against completions. If a later $.clock.after throws, cancel the WAIT deadline; when idle return timeout at once, otherwise race submit against turn completions and session end; a completion returns timeout, and after session.end return timeout at once, as on the clocked path. Submit settlement still records its own outcome, including late settlement after timeout; pending submits are never recorded as submit-rejected for clock failure. turn.complete wakes waiters before any await, then ensureTicking, then next(e).
   ```

5. **Fallback: the prompt box.** A refused pointer (no registered session of that name), a consumed one, or one the model ignored leaves the file to the tick, which delivers it as before under all existing holds. Senders without a session (supervisor lifecycle legs, job results, cron writers) always use the fallback.

## Residue, stated plainly

- Submit wait behavior is specified in row J: one 60-minute turn WAIT deadline plus at most six full submit windows. After session end, both clocked and clockless paths return timeout immediately and record unresolved, releasing the tick without a final window. Its admission ticket still waits for submit settlement or owner death.
- The model must act on the pointer. A seat that ignores it is served by the tick as before; a seat that drains it has read the mail once. The receipt shows which happened.
- Known limit: a delivery arriving in a turn's tail may be read by the engine in a NEW turn. Its admission releases at the old turn's completion, so the tick may claim the file before the new turn drains it and the body can arrive twice. This rare case requires both the tail timing and the model not draining; it is accepted over parking a message.
- A pointer that reaches the engine while a clear is executing: not measured. The hold is re-checked when the pointer becomes a prompt, so a clear that began after the queueing still drops it; the rollout measures the case on the first seat.
- `broadcast` is never announced (a documented limitation); its recipients read it through their ticks as before.

## Follow-ups accepted post-merge (Rule-26 round 11)

- `session.end` retire waits behind the serial marker chain and a seat-name read inside the engine's end budget; a publish in flight at exit can leave a fresh marker for up to 15 min (safe direction). Cache the published seat and write the retire without waiting on a queued publish.
- Hold composition (`cycleHold ?? supervisorHold`) is hand-written in the tick, `refreshMarker` and `pointerHold`; one `holdOf` helper.
- Marker state lives in five module variables and two throttles, `markerAt` mutated outside the serialised job; one marker object, decisions inside the job.
- The tick stops delivering while any ledger entry is unresolved (`if (unresolved) return` after the freeze branch), lifecycle legs included. Pheme 2026-10-29: one `submitting:unresolved` claim from 20:11Z held the supervisor's capsule request and nudge at 23:45Z and 23:50Z while the seat was idle, the supervisor withdrew them after its 300 s no-ledger-activity ceiling, and the refresh cycle failed until the operator cleared by hand; the resume legs were then held the same way until `/delivery-reconcile`. The pointer shape does not touch this path (supervisor legs always take the tick). A stuck claim should not freeze lifecycle legs; either let lifecycle legs pass the unresolved gate or settle a stuck claim automatically when its pid and generation are this process's and no submit is in flight.
