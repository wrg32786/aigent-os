# Native pointer: the Room as the record, the engine as the doorbell

*fleet-delivery mod 0.4.0, 2026-10-29.*

## The problem it removes

Seat-to-seat mail in the fleet was a Room file (the record) delivered by typing it into the recipient's prompt box (the transport). Every stall seen on the live seats in October 2026 was a stall of that transport or of the claim state that guards it, never of the record:

| ledger state | what it meant |
|---|---|
| `deferred:composer-busy` | the recipient's prompt box held a draft |
| `deferred:supervisor-hold` | the supervisor froze the inbox for a refresh handshake |
| `deferred:refresh-hold` | the runner's cycle file was not idle |
| `submitting:unresolved` | a claim with no submit in flight; everything behind it waited for an operator's `/delivery-reconcile` |
| (DaVinci, 2026-10-29 16:36Z) | a message typed during the clear landed as the first prompt of the new session, ahead of the resume |

## The design, after six review rounds

The first six rounds of review were spent on a design where the mod carried the body natively, matched it against the Room file, timed a confirmation window and read the transcript to decide "delivered". Each round opened a new seam in the same three places (the match, the clock, the confirmation). The shape that ships has none of them:

1. **Record unchanged.** `room_send` writes the envelope file into `<roomRoot>/inbox/<seat>/`; the per-seat ledger and the inbox/claimed/processed folders keep their meaning; read receipts, replay and audit stay file-based.
2. **A pointer, not the body.** The sender's mod hooks `tool.call` for `mcp__agent-room__room_send`; after the Room server answers, and before the tool's answer goes back to the model (the send is awaited inside the hook, bounded at 5 s, so no `$` is used after the hook returned), it sends `Room mail for <seat> from <sender>: <file>` plus one line telling the model to call `room_drain`. The receiver treats every spelling of a peer delivery alike (`peer`, `peer-send-message`, and a task notification with that subkind) and judges a prompt by its own Room, never by the framing: every pointer line in the text is found, and one naming this seat whose file is unread in inbox/ is the pointer; a bare pointer with no file behind it still meets the holds; a quoted pointer line whose file is already read is ordinary mail and is never dropped. The pointer is addressed to the session id the recipient's marker carries (`$.session.send({ to: { sessionId } })`), never to a bare name: the engine resolves a name the way SendMessage does, and a subagent of the sender named like the seat would take it with `isDelivered` true. A `/clear` gives the recipient a new id and its next marker write carries it; a pointer to the old id is refused and the file waits for the tick. The engine queues it inside the recipient: a turn of its own when idle, read inside the running turn otherwise. Nothing to match, nothing to forge: a forged pointer drains real mail, harmlessly.
3. **The Room's own consumer reads.** The recipient's model calls `room_drain`, which returns the unread inbox and moves each file to processed/ as read. **Semantics change, documented:** the 0.3.0 tick delivered every Room file as its own prompt; `room_drain` collapses same-sender, same-thread messages, so two pointers from one sender on one thread yield one drain and the older message is consumed unshown (the vault's known supersede failure, now reachable on mod-owned seats). The pointer text therefore says: drain, and if the named file is not among the returned items, read it with `room_history` with `unread_only` false; a collapsed message is in processed/ and recoverable only that way. **Attention double-delivery:** a pointer read inside a running turn that the model does not act on would otherwise be followed by the tick claiming the file and submitting its body as a second turn, with the later drain returning nothing. The tick never claims while the main loop has a turn in flight (`turn.start` to `turn.complete`/`turn.abort`): its own submit could not enter before the session is idle anyway, and the file stays visible to the model's own `room_drain`; `turn.complete` ticks again and delivers whatever was not drained. The mirror case, claim-before-pointer (the tick claimed and submitted the file before the asynchronous announce landed): the receiver drops a pointer whose file is no longer in the inbox, so the model is not told to go and find a message the tick has already delivered. The mod writes nothing for a natively read file; to its tick a drained file is absent, a case it already handles. One body read either way: a file lies in exactly one of inbox/ (`room_drain`'s) and claimed/ (the tick's).
4. **Two fences.** A seat is announced to only while its own mod publishes a fresh marker in the shared Room (`state/native/<seat>.json`: mod-owned, version 0.4.0 or later compared numerically, under 15 min old, rewritten at most every 5 min by the tick and by the tick's timer when a submit blocks the tick). The marker is published only while both holds (refresh cycle, supervisor) are clear and is retired by overwrite (`owner: retired`) under a hold, when the mod no longer owns the seat, and at session end (only a marker that reads back as this session's: this module's stamp, or this session's id after a plugin hot reload; a second session resolving to the same seat, such as a `claude -p` courier, never takes the live seat's marker down and never overwrites a fresh mod-owned marker that is not its own, so pointers cannot flap to the courier; when the file stops reading as the live seat's own and is not another live session's fresh marker, the live seat re-publishes on its next tick regardless of the 5-min throttle; a marker left by a dead process ages out in 15 min), so a held, supervisor-owned, older or parked seat gets no pointer and its tick or supervisor delivers the file; the sender falls back on its own. The marker is written with `$.fs.write`, not the atomic host write: a torn read on the sender's side parses as no marker and falls back, which is the safe side. The safety net: the recipient re-checks the holds at the moment a prompt that IS a pointer (decided by the receiver from its own Room, not from the framing: a line naming this seat and a file that is in its inbox/, being claimed, or in claimed/; a quoted pointer line whose file is already read is ordinary mail, and a bare pointer for another seat is dropped) becomes a prompt, not at arrival, whoever owns the seat by then: while its refresh cycle is not idle or its supervisor holds the seat, the pointer is dropped and the file waits. Neither fence runs while the mod is inert (`installRoot` unset). The turn bookkeeping resets at session start and end, so a turn whose completion the hook never hears cannot leave the tick idle for the life of the process. A submit's timeout clock runs only while no main turn is in flight (bounded at six timeouts, the supervisor's own 60-minute busy ceiling), so a lifecycle leg filed during a long turn stays `submitting` rather than becoming `submitting:unresolved`. A pointer that entered marks its files (every unread file it names) for the tick, before the prompt goes on, until the turn that reads it completes: the running turn it was delivered into (the prompt carries that turn's id), or else the first main turn that starts after it (a pointer queued behind a running turn is read by the next one), and the tick never claims while a main turn is in flight (turns paired by id from `turn.start` to `turn.complete`), so the file stays visible to the model's own `room_drain`; the decision is made once per tick for the whole queue, and the supervisor's lifecycle legs are exempt (their claim line is what the supervisor watches for, and their submit was always queued until idle). A claim in flight across the rename spawn is visible to the fence, which drops a pointer for that file. A pointer addressed to another seat is dropped whether held or open. The hooks module and its test are type-checked against the vendored engine typings and run under `claude plugin test` in CI. The fence fails closed for pointer-shaped text: a pointer for any seat, and a pointer whose hold check cannot be read, is dropped under a hold. Peer text that merely mentions Room mail or `room_drain` has no file behind it and is left to the engine. So a pointer can never become the first prompt of a post-clear session ahead of the resume, even when the clear started after the pointer was queued.
5. **Fallback: the prompt box.** A refused pointer (no registered session of that name), a consumed one, or one the model ignored leaves the file to the tick, which delivers it as before under all existing holds. Senders without a session (supervisor lifecycle legs, job results, cron writers) always use the fallback.

## Rollout (fleet of four, staged like the cf08677 cutover)

1. Merge; the mod is a user-scope plugin read from `C:\dev\aigent-os-wt-mods`: `git -C C:/dev/aigent-os-wt-mods checkout --detach <merge-commit>` then `claude plugin update fleet-delivery@aigent-os`; `claude plugin list` must read 0.4.0.
2. Each seat loads 0.4.0 at its own relaunch (park, Will closes the window, relaunch through the seat's shortcut). Order: Titus, Metis, DaVinci, Pheme in her newsletter-safe window. A seat on 0.3.0 and a seat on 0.4.0 interoperate: a 0.3.0 recipient publishes no marker, so it is never announced to; its tick delivers the file as before.
3. Receipt per seat on aigent-os-program #49: `claude plugin list` version, one labelled Room message each way with the sender's `pointer queued` log line, the recipient's transcript rows showing the pointer and its `room_drain` call returning the file, and one message sent while the recipient is mid-turn. The `pointer queued` line alone is not delivery evidence.
4. Not in this change: the supervisor's inbox freeze and the runner's refresh hold stay as they are; they govern the fallback path. Repointing the legacy-runtime hooks on the supervisor seats remains a separate follow-up.

## Residue, stated plainly

- The model must act on the pointer. A seat that ignores it is served by the tick as before; a seat that drains it has read the mail once. The receipt shows which happened.
- A pointer that reaches the engine while a clear is executing: not measured. The hold is re-checked when the pointer becomes a prompt, so a clear that began after the queueing still drops it; the rollout measures the case on the first seat.
- `broadcast` is never announced (a documented limitation); its recipients read it through their ticks as before.

## Follow-ups accepted post-merge (Rule-26 round 11)

- `session.end` retire waits behind the serial marker chain and a seat-name read inside the engine's end budget; a publish in flight at exit can leave a fresh marker for up to 15 min (safe direction). Cache the published seat and write the retire without waiting on a queued publish.
- Hold composition (`cycleHold ?? supervisorHold`) is hand-written in the tick, `refreshMarker` and `pointerHold`; one `holdOf` helper.
- Marker state lives in five module variables and two throttles, `markerAt` mutated outside the serialised job; one marker object, decisions inside the job.
- The tick stops delivering while any ledger entry is unresolved (`if (unresolved) return` after the freeze branch), lifecycle legs included. Pheme 2026-10-29: one `submitting:unresolved` claim from 20:11Z held the supervisor's capsule request and nudge at 23:45Z and 23:50Z while the seat was idle, the supervisor withdrew them after its 300 s no-ledger-activity ceiling, and the refresh cycle failed until the operator cleared by hand; the resume legs were then held the same way until `/delivery-reconcile`. The pointer shape does not touch this path (supervisor legs always take the tick). A stuck claim should not freeze lifecycle legs; either let lifecycle legs pass the unresolved gate or settle a stuck claim automatically when its pid and generation are this process's and no submit is in flight.
